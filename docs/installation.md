# Install SIMcloud for Zoho Commerce

This guide installs the development alpha in an isolated environment controlled by the merchant. It is not a finished one-click Marketplace installation. Keep `live_enabled` false until every applicable [acceptance check](verification.md) passes.

## 1. Prepare a development store

Create a Zoho Commerce development store and a Commerce extension workspace in [Zoho Sigma](https://sigma.zoho.com/). Use South Africa, ZAR and the appropriate local time zone for this integration. Confirm the store's plan supports widgets and API Configurations. The account owner must review the applicable terms and authorize access.

Keep real customer data out of demonstration accounts and public screenshots. See [development-store guidance](development-store.md).

## 2. Prepare isolated connector hosting

Use a dedicated HTTPS deployment for this standalone connector. Do not copy it into SIMcloud's own application or an unrelated live application. Expose only `public/` as the document root.

```text
/absolute/private/merchant-connector/
    server/          Connector PHP source
    app/images/      Bundled product images
    config.php       Merchant configuration, mode 0600
    var/             Private SQLite storage, mode 0700
    public/          Dedicated HTTPS document root
        bridge.php
        .htaccess
```

Build and extract the connector ZIP. Copy `server/config.example.php` to the private `config.php` path. Configure `SIMCLOUD_ZOHO_CONFIG` in both the PHP and cron environments with that absolute path. Never put a real token in the example file or commit it to Git.

The connector requires PHP 8.2+, PDO SQLite, OpenSSL and cURL. Configure PHP logs outside the public root, keep display_errors disabled, and restrict the configuration/storage permissions. Apache hosts must apply the packaged `.htaccess`; other web servers need equivalent denial of log/database files and directory listings. Transfer configuration only over authenticated, encrypted channels with certificate checks.

Generate a unique bridge key and a separate encryption key locally:

```sh
php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'
```

The first output is the bridge key, the second the encryption key. Save them privately. Back up the encryption key separately from the database. Fill the merchant's organization ID, SIMcloud token, actual field API names and Zoho authorization in the private config. Do not expose these values in URLs, issues or screenshots.

## 3. Authorize the merchant's Zoho API access

Create an OAuth client using Zoho's supported flow and request only the required Commerce scopes:

```text
ZohoCommerce.items.READ
ZohoCommerce.items.CREATE
ZohoCommerce.salesorders.READ
```

Store the merchant's client ID, client secret and refresh token privately. Set the correct Zoho region. Account consent and actual API access must be verified; source code and mock tests cannot establish authorization.

The connector does not implement a public hosted signup service or a SIMcloud website account login. OAuth client registration and consent are part of the merchant's private deployment setup.

## 4. Create the secure connection and five API configurations

Create a custom secure connection in the extension workspace, using an API key in the `Authorization` header. Save `Bearer <your bridge key>` in Zoho's credential system. Do not save the SIMcloud API token in the widget, manifest, API URL or Git repository.

In **Build → Widgets → API Configurations**, configure the merchant connector's HTTPS bridge URL. For documentation, a synthetic example is `https://connector.example.com/bridge.php` — replace it with your own deployment.

| Binding | HTTP method | Query |
| --- | --- | --- |
| `health` | GET | `?action=health` |
| `catalogue` | GET | `?action=catalogue` |
| `import` | POST | `?action=import` |
| `fixed` | POST | `?action=fixed` |
| `order` | GET | `?action=order` |

Use the secure connection on each configuration. Set `Content-Type: application/json` for POSTs. The widget supplies the verified organization through `X-SIMcloud-Organization`.

Copy [the empty bindings example](../config/zoho-bindings.example.json) to a local private JSON file and fill the five values with the exact `ac_*` names generated in your workspace. Keep this metadata out of the public repository even though it is not a token.

Also save the single connection-metadata object generated by Zoho in a separate private JSON file. The supported fields are `connectionLinkName`, `connectionName`, `serviceName`, `userAccess`, `isUserDefinedService` and `sharedBy`. Copy actual metadata from your workspace rather than guessing an identifier. Do not put the bridge key, OAuth secret or SIMcloud token in this file.

Build your locally configured widgets:

```sh
python3 scripts/build.py \
  --bindings /absolute/private/zoho-bindings.json \
  --connection /absolute/private/zoho-connection.json
```

Without these options, builds remain unbound and contain no account-specific API names or connection metadata. Locally bound ZIPs are deployment artifacts for the intended merchant; do not attach them to public releases or issues. Public releases use the default unbound build.

## 5. Upload the widget packages

Upload `simcloud-zoho-widget-*.zip` under **Build → Widgets → New Widget**. The manifest declares global-sidebar and sales-order-detail locations. Upload `simcloud-zoho-settings-*.zip` separately through **Configure → Global Fields → Upload Widget** for installation settings. Do not upload the PHP connector ZIP as a widget.

Use Zoho's private testing flow to install in the development store. Authorize the secure connection and initially restrict access to administrators. Verify the settings widget, global sidebar and sales-order sidebar in the installed extension. Upload success alone is not runtime acceptance.

The widget uses Zoho's SDK 2.0. The [official API Configuration guide](https://www.zoho.com/commerce/developer/widgets/api-configurations/) documents the native configuration controls and secure request fields.

## 6. Configure customer-input fields and product layouts

Create recipient and meter fields, select customer input, include their values in Sales Orders and exclude sensitive values from public descriptions and PDFs where unnecessary.

| Input | Generic connector default | Relevant products |
| --- | --- | --- |
| Recipient mobile | `cf_simcloud_recipient` | Airtime, data and electricity |
| Meter number, single-line text | `cf_simcloud_meter` | Electricity |

Use the actual Zoho-generated API names in private configuration. A text meter field preserves leading zeros. Configure recipient-only, electricity and VAS layouts, and assign them to the appropriate products. VAS must not ask for a meter. Unrelated products must not inherit prepaid inputs.

Zoho's [custom-field guide](https://help.zoho.com/portal/en/kb/commerce/user-guide/settings/general-settings/articles/custom-fields) describes layout assignment. Verify the actual storefront: correct admin selections alone do not prove visibility or required-field validation. Submit missing, malformed and valid synthetic input, then inspect each order line's `item_custom_fields`. Stop acceptance if the storefront freezes or shows the wrong fields. This alpha does not automatically create or assign these layouts.

## 7. Load products and review prices

Open SIMcloud and select **Load my products**. Setup reads balance and catalogues; it does not submit a prepaid purchase. Select products and choose **Import selected**. New data/VAS products use the API amount as the initial retail price. Existing names, prices and images are preserved.

Use **Add airtime or electricity** for fixed-value products. Review taxes, margins, service/non-shipping behaviour and quantity limits before selling. Repeat an import to verify duplicates are prevented and merchant edits remain intact.

## 8. Configure the order workflow and worker

Create an authenticated paid-order workflow that POSTs `{"order_id":"<sales order ID>"}` to the merchant connector's `bridge.php?action=enqueue`, using its secure connection and organization header. Verify Zoho's actual order-ID substitution. The connector fetches the order independently and does not trust webhook payment claims.

Run the worker every minute using a compatible PHP CLI and the same private configuration:

```sh
SIMCLOUD_ZOHO_CONFIG=/absolute/private/merchant-connector/config.php \
  /path/to/php /absolute/private/merchant-connector/server/worker.php
```

Verify private logs, locks, backups, sender configuration, inbox delivery and bounce handling. A successful mail function return does not establish delivery. The workflow and cron are manual developer setup in this alpha.

## 9. Complete acceptance before enabling purchases

Complete [the release checklist](verification.md). Verify actual online gateway payment fields and configure exact `verified_payment_modes`. Require account-owner authorization for the final recipient, network/product, amount and reference before each funded test. Only enable `live_enabled` after successful acceptance.

## Uninstall and data retention

1. Disable the order workflow and set `live_enabled` false.
2. Reconcile accepted purchases through their saved IDs before retiring the worker.
3. Remove the widget from Zoho and revoke its OAuth authorization and secure connection.
4. Rotate or revoke connector credentials as appropriate; check dependencies before rotating a token shared with another client.
5. Retain or erase private ledgers, keys and backups according to the merchant's accounting/privacy obligations.
6. Preserve merchant products and order history unless the merchant specifically requests their removal.

Removing a widget does not automatically remove an external connector or its private ledger.
